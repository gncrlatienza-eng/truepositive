# TruePositive — 9-Week Agile Sprint Plan

**Team:** Solo developer + Claude (code generation), user reviews and commits.
**Cadence:** 9 sprints, 1 week each (Monday–Sunday). (Originally 8 weeks; Sprint 7 — Multi-Device Visibility — was added mid-plan, on 2026-08-15, pushing the original Sprint 7/8 back a week each. See that sprint's entry for why.)
**Window:** 2026-08-10 → 2026-10-11.
**Scope:** The full feature set defined by an interactive UI mockup and a project manifest, both kept in `reference/` (gitignored, not committed to this repo), minus the mobile app (explicitly deferred — see [Out of Scope](#out-of-scope)).

This plan is deliberately concrete: every sprint maps to specific screens/sections in the mockup (`isDashboard`, `isLogs`, `isAlerts`, `isIncidents`, `isReports`, `isIntel`, `isSettings`, and their modals) rather than generic milestones. The `is*`/state-field names referenced throughout come from that mockup — ask the project owner for a copy if you need to see the screen behind a name that isn't self-explanatory.

---

## Product Goal

Ship a working, **beginner-friendly** SIEM MVP — built to teach people new to security operations how detection actually works, not just to run in production for veteran analysts. Real SIEMs (Splunk, Sentinel, QRadar) bury newcomers under configuration and jargon before they see a useful alert; TruePositive keeps the same core workflow — an analyst signs up, deploys an agent, selects log sources, watches logs flow into a dashboard, gets tuned alerts instead of noise, investigates and resolves incidents, pulls reports, and looks up threat intel — end to end, running locally via `docker-compose up` and deployable to Vercel/Railway/Render — but with a UI, onboarding path, and in-product explanations a new learner can actually follow. Concretely: a first-run "get set up" checklist instead of a blank dashboard, plain-English explanations on every non-obvious metric (risk score, SLA, triage time), and a starter library of pre-built detection rules with "what this catches and why" descriptions rather than an empty rule editor.

**Multi-device, not just single-host** (clarified 2026-08-15, see Sprint 7): one org isn't limited to one agent — deploy one per machine you want visibility into (a family's PCs, a small team's workstations/servers), and the dashboard already aggregates across all of them. The backend/dashboard itself isn't "installed on" any monitored device — every agent, wherever it runs, just points at the same central server via its Server URL. Sprint 7 adds the first layer of per-device visibility (counts per agent, one markable as "Primary") on top of that already-working aggregation.

## Sprint Rules

- **Sprint length:** 1 week. Monday: review sprint goal, pull tasks. Friday/weekend: demo to self (run the feature), retro (what slipped, why), update `docs/SPRINT_PLAN.md` checkboxes.
- **Definition of Ready:** a task can be pulled into a sprint only if the screen/field it implements is traceable to the mockup or manifest — no undefined scope.
- **Definition of Done (per task):** code runs locally, matches the mockup's layout/interaction for that screen, has no unhandled error states on the happy path, and is committed by the user after review.
- **Daily overhead:** none formally tracked (solo project) — but each sprint's Acceptance Criteria section doubles as the sprint's task board.

## Sprint 3 — Agents & Log Collection
**Dates:** Aug 24–30
**Goal:** A real agent can register, heartbeat, and its configured log sources are persisted and manageable.

**Backend**

- [x] Encrypted credential storage for remote source auth (SSH key / password; Kerberos accepted by the enum but rejected with 422 as "coming soon", matching the WinRM/Syslog stub below). Fernet symmetric encryption, key from `CREDENTIAL_ENCRYPTION_KEY` (no default — fails fast if unset, same pattern as `JWT_SECRET`). Decrypted plaintext never returned by any endpoint.
- [x] Log source CRUD (local + remote). SSH only for real; WinRM/Syslog return 422 "coming soon" per this sprint's own risk note below.

**Frontend**
- [x] Settings → Sources tab: lists agents (connection status/last-seen, each deletable) and configured sources, pause/resume, edit, delete, "Connect data source" modal (SSH enabled; WinRM/Syslog/Kerberos shown disabled, "coming soon"). Deletes and Redeploys go through a styled confirmation modal now (not the browser's native `confirm()`), applied consistently to log source and whitelist-entry deletion too. Non-connected agents also get a "Redeploy" button — re-running the *same* already-downloaded agent already reconnects it on its own, but if that file/config is lost there was no way to get another (the raw key is never stored server-side, only its hash); Redeploy rotates the key and hands back a fresh, ready-to-run download.
- [x] Settings → Whitelist tab: allowlist view (BLOCKLIST toggle shown disabled, "coming soon" — the model has no block/allow kind column and the AC only calls for allowlist behavior), "Add entry" modal with type/value/reason/expiry.

**Acceptance Criteria**
- [x] An agent process (can be a scripted stub for this sprint) can register with real credentials and appear as "connected" in onboarding step 2 and in Settings → Sources. Implemented as a real, runnable, dependency-free script (`agent/tp_agent.py`) rather than a curl demo — it genuinely registers and heartbeats over HTTP, and is what flips the dashboard's live-polling UI to "connected." - [x] Whitelist entries persist and are enforced at the query layer (excluded from later log/alert views). `whitelist_service.exclude_whitelisted()` is a reusable filter (`column.notin_(active, non-expired values)`) plus a `GET /settings/whitelist/effective` endpoint to inspect the active set. Since no log/alert list endpoint exists yet (Sprint 5), this is proven with a test that inserts real rows into the `logs` table and asserts the filter drops only the actively-whitelisted one — genuinely enforced at the query layer, not just documented as a plan.

Also fixed pre-existing bug found while testing this sprint: `/onboarding` was wrapped in `GuestRoute`, which redirected any signed-in user to `/app` — since step 1 signs the user in immediately, onboarding steps 2 and 3 were unreachable after a real signup since Sprint 2 (nothing in those steps called the API yet, so it went unnoticed).

- [x] **Real bug found and fixed during end-to-end browser verification, not by static review**: switching directly from one drill-in panel to another of a different type (e.g. Severity → Rule) crashed the entire app to a blank page. Root cause was a stale-render race in `MetricPanel.jsx` — clicking a new panel row changes `panel.type` synchronously, but the effect that resets fetched `data` for the new panel only runs *after* that render commits, so for one render the *previous* panel's data (wrong shape) got passed into the *new* panel's component (e.g. a Severity-shaped response into `RulePanel`, which reads `top_sources`/`other_rules` — fields Severity's schema doesn't have) → uncaught `TypeError` → whole React tree unmounted, since there was no error boundary anywhere to contain it. Fixed by keying the panel drawer's component instance to the panel's identity (`type:key`), forcing a clean remount — and therefore fresh state — on every panel-type switch, instead of relying on an effect to clear stale state after the fact. Also added a top-level `ErrorBoundary` around the routed page content (contains any future render crash to the page instead of the whole app) and a `.catch()` on the panel fetch (shows an inline error instead of hanging blank on a failed request). Reproduced the exact crash first via a scripted rapid panel-switch (console showed `TypeError: Cannot read properties of undefined (reading 'length')`, page fully blanked), then confirmed the same sequence causes zero console/page errors after the fix.

**Acceptance Criteria**

## Sprint 5 — Logs & Alerts
**Dates:** Sep 7–13
**Goal:** Analysts can search raw logs and manage the alert pipeline end to end.

**Backend**
- [x] Log query endpoint: search, filter (by source/severity/event_type/hour), sort, pagination, CSV export. `GET /logs` + `GET /logs/{log_id:int}` + `GET /logs/export.csv`, all org-scoped. First endpoint in the codebase to need real pagination — established the `{items, total, limit, offset}` convention here.
- [x] Alert rules engine: rule storage + evaluation against incoming logs. Deliberately a small, structured condition schema (`event_type` exact-match + `min_severity` threshold) rather than free-form JSONB — evaluated synchronously at ingestion time (no scheduler, same "no background sweep" philosophy as Sprint 3's agent staleness check), one `Alert` created per matching rule per log.
- [x] Alert CRUD + ack/escalate state transitions. `GET/PATCH /alerts`, `GET/POST/PATCH/DELETE /alerts/rules`. Reuses the existing `status` + `updated_at` columns rather than adding dedicated `acknowledged_at`/`escalated_at` timestamps — no real need for them yet, and the dashboard's MTTR panel already derives duration the same way.

1. **Multi-Device Visibility (Sprint 7)** — drop entirely; the Agents drill-down keeps its Sprint 5 behavior (status/last-seen, no per-agent counts or primary badge). Added mid-plan and least core to the original single-org detection loop, so it's the first thing to give up.
2. **Threat Intel page** — drop entirely; keep IOC data model for Phase 2.
3. **Automation/Playbooks** — keep manual incident response, drop automated actions.
4. **Reports beyond Daily** — ship Daily only; Weekly/Monthly/Compliance/Builder/Library become Phase 2.
5. **Incident richness** — keep the incident list + basic resolve/escalate; drop the notes/history sections and reassign modal.

## Out of Scope

- **Mobile app (React Native + Expo)** — present in the project manifest but not in the UI mockup. Not scheduled anywhere in this plan. A minimal Expo scaffold exists in `mobile/` for future Phase 2 work only.
- **Advanced ML/behavioral analytics** — manifest's Advanced Feature #6; needs real production log volume to be meaningful, explicitly deferred.
- **Third-party integrations (Slack/Jira/AWS/Azure/Splunk)** beyond the stubbed Slack-notify playbook action.
- **Full per-device dashboard filter/switcher** (re-scoping every Overview chart to one specific agent, not just the Agents drill-down's per-agent counts) — the larger of the two options considered for Sprint 7; deferred in favor of the lighter version there. Revisit if the lighter version proves not to be enough once real multi-device households/teams are actually using it.
