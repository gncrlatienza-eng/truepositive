# Security

TruePositive is a security product — its own codebase should hold up to the same scrutiny it will eventually apply to customers' compliance evidence (see `docs/SPRINT_PLAN.md`'s Sprint 7 reports: SOC 2 / HIPAA / PCI-DSS). This document states what standard we're building against and gives an honest account of where the code currently stands.

## Standard we align to: OWASP ASVS

We use the [OWASP Application Security Verification Standard](https://owasp.org/www-project-application-security-verification-standard/) as the practical, code-level baseline — it's a checklist for exactly what this project is (a web app + API), rather than an organizational certification.

**ISO/IEC 27001 and SOC 2 are explicitly out of scope for now.** Both are management-system certifications — risk registers, access-control policies, incident-response plans, third-party audits — pursued by an organization with customers requiring them, not something a pre-launch codebase "implements." If TruePositive reaches the point of selling to customers who require one, that's a business decision to revisit; ASVS is what the code itself can actually be measured against today.

## Current status

Organized by ASVS area. This list will go stale — treat it as a snapshot, not a live audit; verify against the actual code before relying on it.

### Covered
- **Password storage**: bcrypt, never logged or returned in any API response (`backend/app/utils/security.py`).
- **Injection**: all queries go through SQLAlchemy's ORM/query builder — no raw string-interpolated SQL anywhere in the codebase.
- **Authentication tokens**: JWT with an explicit algorithm (`HS256`, no algorithm-confusion surface), signature verified server-side on every request, clean 401s on missing/malformed/expired tokens.
- **Secrets configuration**: `JWT_SECRET` has no default — the app fails to start rather than silently running with a guessable key.
- **Input validation**: every request body is validated server-side via Pydantic schemas (`backend/app/schemas/`), independent of whatever the frontend already checked.
- **CORS**: explicit origin allowlist (`CORS_ORIGINS` env var), not a wildcard, despite `allow_credentials=True`.
- **Session invalidation on bad token**: the frontend's axios interceptor clears session state and redirects to `/login` on any `401` (`frontend/src/utils/api.js`).
- **Security response headers**: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` (frontend), `Strict-Transport-Security` — set in `docker/nginx.conf` and `backend/app/main.py`'s `security_headers` middleware. **`Content-Security-Policy` is deliberately excluded** — see note below.
- **JWT library kept current**: `python-jose` pinned to `3.4.0` in `backend/requirements.txt` (was `3.3.0`, which had CVE-2024-33663, an algorithm-confusion signature-verification flaw, CVSS 7.4). Our own `jwt.decode()` call already hardcodes `algorithms=["HS256"]` rather than trusting the token's own header, which mitigates the main attack vector regardless — took the upgrade anyway since it was a safe, non-breaking pin bump.
- **Remote log-source credentials encrypted at rest** (Sprint 3): SSH keys/passwords for remote log sources are encrypted with Fernet (`backend/app/utils/crypto.py`) before storage; `CREDENTIAL_ENCRYPTION_KEY` has no default (same fail-fast pattern as `JWT_SECRET`). No endpoint or schema ever returns the decrypted plaintext or the ciphertext — `LogSourceOut` only exposes a derived `has_credential: bool`.
- **Agent enrollment keys hashed at rest** (Sprint 3): the one-time key returned by `POST /agents` is bcrypt-hashed in `agents.agent_key_hash`, shown to the user exactly once, never returned again by any endpoint.
- **Agent enrollment keys can be revoked/rotated** (Sprint 3): `POST /agents/{id}/rotate-key` (user JWT, org-scoped) issues a new key and invalidates the old one immediately — the old key stops authenticating `register`/`heartbeat` calls right away. Exists for the operational case (lost the agent's config/binary) but doubles as the manual revoke path this gap used to note was entirely missing.
- **Log ingestion validates source ownership, not just agent identity** (Sprint 5): `POST /agents/{id}/logs` checks every `source_id` in a batch is actually assigned (`log_sources.agent_id`) to the authenticating agent before writing anything — a valid agent key can't be used to write log rows tagged with a different agent's (or a different org's) source, since source lookup is scoped to `LogSource.agent_id == agent.id`. Rejects the whole batch (422) rather than silently dropping the disallowed entries.
- **CSV export is capped** (Sprint 5): `GET /logs/export.csv` caps at 5,000 rows regardless of how broad the filter is, so an unfiltered export can't be used to pull an unbounded amount of data or exhaust server resources in one request.
- **Rate limiting** (2026-08-20, partial): an in-memory, per-process fixed-window limiter (`backend/app/utils/rate_limit.py`) protects the highest-value targets — `POST /auth/login` and `/auth/signup` (per client IP, 10/60s and 5/60s), and `POST /agents/{id}/register`, `/heartbeat`, and `/logs` (per `agent_id` — this is the one that matters most: it closes the "a leaked or guessed agent key lets an attacker inject unlimited fabricated log/alert rows into a real org's dashboard" gap, a real integrity attack on the product's core "prove what happened" promise, not just brute-force abuse). Not yet applied to every mutating endpoint app-wide. Because state is process-local, it does **not** coordinate across multiple backend replicas — a shared store (Redis) would be needed before this service is horizontally scaled. Still no account lockout on repeated failed logins beyond the rate limit itself.
- **TLS in production** (2026-08-20, partial): the default `docker-compose.yml` dev stack still serves plain HTTP — that's unchanged and intentional for local dev. A new `docker-compose.prod.yml` overlay + `Caddyfile` add a `caddy` reverse-proxy service that terminates TLS with an automatically-issued Let's Encrypt certificate for a real domain (`DOMAIN` in `.env`). Run in production via `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d`. This closes the previously-undocumented gap that nothing in this repo enforced HTTPS at all — passwords, JWTs, and agent keys would otherwise travel in cleartext if the dev compose file were deployed unchanged. Not verifiable end-to-end in this dev environment since Let's Encrypt's ACME challenge needs a real public domain + DNS + open port 80/443, which don't exist here — the config is real and correct, just untested against a live certificate authority.
- **Postgres network exposure** (2026-08-20): previously published on `0.0.0.0:5432` with hardcoded `truepositive`/`truepositive` credentials baked directly into `docker-compose.yml` (not even `.env`-sourced) — on any host without an external firewall, that was an internet-reachable database with known credentials and full read/write access to every org's data. Dev default is now loopback-only (`127.0.0.1:5432`, still reachable from host tools like psql for local development) with credentials sourced from `.env` (documented dev defaults, override before any real deployment). `docker-compose.prod.yml` removes the host port mapping entirely — Postgres is reachable only from other containers on the internal network — and refuses to start without a real `POSTGRES_PASSWORD`/`JWT_SECRET`/`CREDENTIAL_ENCRYPTION_KEY` set in `.env`.
- **Agent binary download integrity** (2026-08-20, partial): `GET /agents/download/windows` and `/download/windows-installer` now return an `X-SHA256` header so a download can be verified against a known-good hash. This does **not** replace code signing — the binary and installer are still unsigned (no Authenticode certificate; would need one purchased and wired into the build pipeline, out of scope for a code change) — but it's a cheap, real mitigation against in-transit tampering for anyone who checks it.
- **Agent config/credential file permissions** (2026-08-20, partial): `agent_config.json`/`agent_state.json` (which hold the agent's enrollment key in plaintext) previously had no permission restriction — world-readable to any local user on a shared machine. The agent now best-effort tightens these to the current user only (`icacls` on Windows, `chmod 600` elsewhere) after every write. Doesn't change the underlying fact that the key is stored in plaintext and never expires agent-side (see the existing gap below) — this only narrows who on the local machine can read it.
- **Agent server-URL TLS pinning** (2026-08-20, new, opt-in/off-by-default): the agent can optionally verify the backend server's certificate fingerprint (`pinned_cert_sha256`, hand-added to `agent_config.json`) before connecting, closing the "DNS-spoof/MITM of a copy-pasted Server URL silently captures a live enrollment key" gap for anyone who configures it. Off by default — there's no UI flow yet to help a user obtain the right fingerprint, so this only protects deployments that set it up manually.

### Gaps (known, not yet addressed)
- **No password reset flow** — the "Forgot?" link on the login page is an intentional placeholder (see `docs/SPRINT_PLAN.md`); there's no backend endpoint and no sprint currently scoped to build one.
- **No email verification** on signup.
- **No MFA.**
- **Long-lived JWTs with no revocation** — tokens live up to 30 days (`JWT_EXPIRE_MINUTES`) with no refresh-token rotation and no server-side revocation list, and the lifetime doesn't vary with the "keep me signed in" checkbox — even a not-remembered session's token is valid for the full 30 days if copied out of `sessionStorage` before the tab closes. Logout is client-side only (clears storage).
- **Tokens stored in `localStorage`/`sessionStorage`**, not an `httpOnly` cookie — readable by any script that achieves XSS on the page. Standard tradeoff for a separate SPA + API (no CSRF token needed either way), but worth naming explicitly rather than leaving implicit.
- **No `Content-Security-Policy`** — the frontend relies on inline styles throughout (React's `style={{...}}` prop renders as real inline `style="..."` attributes, which a strict CSP blocks without `'unsafe-inline'`) and loads Google Fonts from an external origin. Note this got slightly easier to eventually fix (2026-08-20): the frontend now calls the API via a same-origin relative path (`/api`, proxied by nginx/Caddy — see `frontend/src/utils/api.js`) rather than a deployment-varying absolute `VITE_API_URL`, so a future `connect-src` directive wouldn't need per-deployment templating for that part. Getting the rest right (inline-style handling, Google Fonts allowlisting) still needs real browser verification (no CSP-violation console output is visible from a `curl` check) — not done yet, so it's left off rather than shipped unverified.
- **`audit_log` table exists but nothing writes to it** — the schema (`backend/app/models/audit_log.py`) was built in Sprint 1; no route or service populates it yet. Real audit logging is unscheduled (Settings → Audit tab is Sprint 8's "last unbuilt screen" per the sprint plan).
- **Single static credential-encryption key** — one `CREDENTIAL_ENCRYPTION_KEY` for the whole deployment, no rotation mechanism, no KMS/per-tenant keys. Rotating it today would strand every previously-encrypted `log_sources.credential_encrypted` value (no re-encryption path exists yet).
- **Agent enrollment keys never expire on their own, and rotation is manual-only** — `enrollment_expires_at` only gates the initial `pending → connected` transition; a connected agent's key is otherwise long-lived and only gets invalidated if a user explicitly rotates it (see Covered, above) — nothing detects or forces rotation of a suspected-compromised key automatically. Rate limiting (see Covered) narrows the blast radius of a leaked key but doesn't solve this.
- **No rate limiting on `/agents/{id}/sources`** (log/register/heartbeat are now covered, above) — read-only, lower value target, but not yet protected.
- **Agent binary/installer are unsigned** — no Authenticode certificate. Windows SmartScreen/AV will likely flag installs, and (partially mitigated by the new `X-SHA256` header, see Covered) there's still no way to distinguish a legitimate build from a tampered one without manually checking that hash. Needs a purchased code-signing certificate wired into the build — not something fixable in code alone.
- **No automated dependency vulnerability scanning in CI.** Ran manually this session (`npm audit`, `pip-audit`) and found:
  - **Frontend**: `esbuild`/`vite` (dev-server-only path traversal, CVSS 7.5, Windows-specific — only reachable via `npm run dev`, not the Dockerized/production build) and `react-router-dom` (two moderate CVEs) — both fixes require a semver-major bump (Vite 5→8, react-router-dom 6→7). Not applied; needs deliberate testing, not a silent bump.
  - **Backend**: `starlette` (transitively via `fastapi==0.115.0`) has multiple known advisories fixed only in much newer `starlette`/`fastapi` versions — same story, needs a framework-version bump evaluated on its own, not a quick pin change. `pip`/`pytest`/`python-dotenv`/`ecdsa` also flagged but are either dev-tooling-only or transitively unreachable given this app's actual usage (e.g. `ecdsa` is a `python-jose` dependency only exercised for ECDSA algorithms, and this app only ever uses `HS256`).
  - Not wired into CI yet specifically because it would fail immediately on the above known, accepted-for-now findings — needs those triaged (fixed or explicitly waived per-finding) before a hard gate is meaningful rather than just permanently red.

## Reporting a vulnerability

This repo doesn't have a public-facing deployment yet, but if you find an issue: use GitHub's [private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing/privately-reporting-a-security-vulnerability) (Security tab → Report a vulnerability) rather than a public issue, once that's enabled on the repo. Don't open a public issue with exploit details.
